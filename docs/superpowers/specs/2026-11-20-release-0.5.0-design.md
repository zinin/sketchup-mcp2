# Design: Release 0.5.0 — honest joinery, world coordinates, socket authentication

- **Date**: 2026-11-20
- **Status**: Draft — awaiting user review
- **Branch**: `fix/p3-joinery` (block B, built first; it carries this document). Blocks A and C
  get their own branches from `master` after the previous block merges, each with a copy of this
  document (`git show <commit>:docs/superpowers/specs/2026-11-20-release-0.5.0-design.md`).
- **Target**: three PRs into `master` without a release, then a release PR for 0.5.0 that ships
  both sides and raises both floors to 0.5.0.
- **Source**: `full-review/full-review-merged.md` (untracked); `M-xx` IDs refer to it. Part 1
  design: `git show ce20bdf:docs/superpowers/specs/2026-10-19-p1-model-integrity-design.md`.
- **Author**: Alexander V. Zinin (with Claude Code)

## 1. Context and intent

Part 1 of the full-review programme (model integrity and safety net) merged as PR #7, and 0.4.0
shipped both sides with the floors-only compatibility scheme. Three P1 items are left — M-03
(coordinate frames of nested entities), M-02 (joinery builds the wrong geometry), M-06 (the
socket has no authentication) — plus the P2 list.

All three change the contract between client and plugin, so they ship in a release that raises
both floors (`docs/release.md` §1). Such a release forces every user to reinstall the plugin,
the expensive step of any release: the maintainer signs the `.rbz` with Trimble, users uninstall
the old version, restart SketchUp and install the new one. Without a floor change nobody has to
reinstall, so Ruby-side fixes reach users slowly. 0.5.0 therefore carries every worthwhile
Ruby-side fix from the P2 list. Python-only and repository-only fixes can ship at any time and
are mostly left out.

The user does not drive the tools directly: an agent picks them, and which ones depends on the
model behind it. That sets the principle for the whole release: **a tool that silently builds
the wrong thing is worse than no tool.** When a tool cannot do the job correctly, it refuses with
a message that says why and what to do instead.

## 2. Goals, non-goals, anti-goals

**Goals**

- No tool reports success for geometry it built wrong: `create_dovetail` and
  `create_finger_joint` are gone, and `create_mortise_tenon` builds a joint that fits or refuses
  (block B, M-02).
- Every `bbox_mm` the MCP surface returns is in world coordinates, and
  `transform_component.position` is a world target, for nested entities as well as top-level
  ones (block A, M-03).
- No mutating tool silently edits every copy of a component: an entity inside a component placed
  more than once is refused (block A, M-03).
- A connection that cannot prove it knows the plugin's token can call no tool, and a process that
  took the port can neither learn the token nor pass for the plugin (block C, M-06).
- The Ruby-side P2 fixes listed in §5–§7 ship with the reinstall that 0.5.0 forces anyway.

**Non-goals**

- Real dovetail and finger joints. They can return later as a separate feature built on world
  coordinates.
- Addressing one placement of a shared component by path (`InstancePath`, `persistent_id`). The
  refusal in §6.2 can be extended to that later without breaking anything.
- Encrypting traffic, or authenticating each message after the handshake (§7.2).
- The rest of P2 and P3 (§11), Trusted Publishing (rest of M-10), and PR #17 (an external
  contribution with changes requested).

**Anti-goals** — the change fails even if the tests pass when it:

- adds a way to switch authentication off or to pick a weak token;
- changes behaviour without saying so in a docstring, an error message or the release notes;
- reformats pinned handler or test source (`CLAUDE.md`: no auto-formatter; update literal pins
  deliberately);
- adds a gem dependency to the plugin or raises the Python floor above 3.10.

## 5. Block B — joinery (M-02)

### 5.1 Withdraw `create_dovetail` and `create_finger_joint`

Remove both from both sides: the MCP tools in `tools.py`; the routes in `handlers/dispatch.rb`;
the handlers and their helpers in `handlers/joints.rb` (`carve_tails`, `carve_pins`,
`carve_board1_fingers`, `carve_board2_slots`, `add_parent_frame_prototype`); the prompt
(`prompts.py`: the typed-tools list, the return shapes, the joinery defaults); README and
`CLAUDE.md` (tool tables, the list of literal-pin tests); and the tests that exist only for them.
Keeping the Ruby handlers behind a removed tool would leave code that builds known-wrong geometry
reachable over TCP. A 0.4.0 client cannot connect to a 0.5.0 plugin once the floors move; before
that, a call to a removed tool gets `-32601 unknown tool`.

The prompt keeps a short joinery note: mortise-and-tenon through the typed tool, other joints
through `eval_ruby`, as in the README example.

### 5.2 `create_mortise_tenon` builds a joint that fits, or refuses

The inputs stay as they are (`mortise_id`, `tenon_id`, `width`, `height`, `depth`,
`offset_x/y/z`, all mm). The handler works in the boards' common parent frame:

1. **Preconditions.** Each failure is a `-32602` that names what is wrong and what is expected:
   - both boards are groups or component instances (as today) and have the same parent;
   - each board's transformation keeps its axes parallel to the parent's (rotations by multiples
     of 90°). Any other rotation is refused: the joint is placed from bounding boxes;
   - the boards touch along exactly one axis: a face of one bounding box lies in the plane of the
     opposite face of the other (within SketchUp's tolerance), and the two faces overlap with a
     positive area — the **contact area**. Separated boards, boards touching only along an edge,
     and overlapping (interpenetrating) boards are refused;
   - the joint rectangle, after the offsets, lies inside the contact area. It may reach the
     area's edge, which makes a mortise open on that side.
2. **Placement.** The joint axis is the axis along which the boards touch. Width and height keep
   today's mapping: for a joint along X, `width` runs along Y and `height` along Z; along Y,
   `width` along X and `height` along Z; along Z, `width` along X and `height` along Y. The
   rectangle is centred on the centre of the contact area. `offset_*` move it along the two cross
   axes; the offset along the joint axis is ignored, as today.
3. **Mortise.** A box `width × height × depth` from the contact plane into the mortise board,
   subtracted with the reversed `Group#subtract` (`cutter.subtract(board)`). A `depth` larger
   than the mortise board's thickness makes a through mortise; that is allowed.
4. **Tenon.** The same box on the tenon board's side, built as a sibling of the tenon board and
   joined to it with `union`, so the tenon board stays one solid (§3).
5. **All or nothing, and checked.** If either solid operation returns `nil` or destroys an
   operand, the whole operation aborts with `-32603`; no half-built joint is committed. The
   bounding-box preconditions cannot see every bad case — a board that does not fill its box at
   the contact area (an L-shape, a notch, a taper), geometry rotated inside an unrotated group,
   or the empty group SketchUp's subtract can return when the cutter shares face planes with the
   board (`handlers/operations.rb` records this for edge ops; here it happens when `depth`
   equals the thickness or the rectangle reaches the contact area's edge). So after both
   operations the handler checks the results and aborts with `-32603` unless:
   - both results are solids;
   - the mortise board lost some volume, and no more than `width × height × depth` (less is
     fine: the pocket may meet an earlier one inside the board);
   - the tenon board gained exactly `width × height × depth` and is one connected solid (a tenon
     that misses the board's real face comes out as a separate shell).

   The `boolean_cuts` field and the module counters behind it (`@_joint_cuts_*`) go away: with
   no partial results they carry no information.
6. **Identity.** Both boards come back as new groups with new ids. Each result gets its
   original's name and layer (tag), and the original group's own material if it had one. Block A
   reuses the helper that does this (§6.3).

The response becomes `{mortise: {id, name, type, bbox_mm}, tenon: {...}}`. Until block A lands,
`bbox_mm` is in the boards' parent frame, as in every other mutating handler today.

## 6. Block A — world coordinates and responses (M-03 and riders)

### 6.1 World coordinates at the MCP boundary

- A helper computes an entity's **world transformation** by walking up: the entity's parent is
  either the model (stop) or a definition; the definition's single instance contributes its
  transformation, and the walk continues from that instance. A definition with more than one
  instance makes the placement ambiguous (§6.2). The walk gives the same answer whether or not
  the user has a group open for editing (§3), so edit contexts need no special case.
- The `bbox_mm` of a group, component instance, face or edge is its bounds' eight corners mapped
  through its world transformation. This replaces parent-frame bounds in `describe_entity`
  (create, transform, set_material, boolean, chamfer/fillet, mortise-tenon) and in
  `get_selection`. `get_component_info` uses the walk instead of the depth-first search from the
  model root (the part of M-19 this release takes). `list_components` and `find_components`
  already report world coordinates and keep their traversal.
- `transform_component`: `position` is a world target. The delta from the world bbox-min after
  rotation and scale is converted into the parent frame with the inverse of the parent's world
  transformation. Rotation and scale are about world axes through the world bbox centre,
  conjugated into the parent frame (`P⁻¹ · R · P`). The literal pin
  `test/test_transform_absolute.rb` is updated deliberately.
- `create_component` keeps its coordinates: at the top level the parent frame is the world, and
  inside an open group SketchUp maps the given coordinates to world (§3). New objects keep going
  into the open group, as SketchUp's own tools do — unless that group is shared: when any
  instance on the open path has a definition with more than one instance, the new object would
  appear in every copy, so `create_component` refuses with `-32602`, naming the component and the
  number of copies and suggesting to close it or make that instance unique first.
- `get_model_info` gains `editing`: the open edit path as `[{id, name, shared}]`, empty when
  nothing is open, so the agent can tell that new objects will land inside a group, and whether
  `create_component` will refuse.

### 6.2 Entities inside shared components

- An entity is **shared** when the walk in §6.1 meets a definition with more than one instance:
  a component placed several times, or copies of a group that still share one definition. For a
  group or component instance the walk starts at its parent, so its own definition does not
  count: moving, painting or deleting one of four chairs at the top level affects only that chair
  (painting makes it unique first, T-16) and stays allowed. For a face or an edge the walk starts
  at the definition that holds it, so a face inside a copied group is shared.
- Every mutating tool refuses a shared target with `-32602`. The message names the component,
  says how many copies the change would affect, and points to `eval_ruby` for editing the
  definition for every copy or for making one instance unique first. Mortise-tenon checks both
  boards.
- Read-only tools: every `list_components` and `find_components` row carries
  `"shared": true|false`; `get_component_info` on a shared id returns the first placement's world
  bbox with `"shared": true`.

### 6.3 Names after solid operations

A result that replaces its target gets the target's name and layer, and the target group's own
material if it had one, through the helper from §5.2 (6). That covers `chamfer_edge` and
`fillet_edge` always, and `boolean_operation` when `delete_originals` is true; the target is the
`target_id` operand for all three operations. With `delete_originals` false (the default) the
target stays in the model, so the result keeps SketchUp's name ("Union", "Difference",
"Intersection"): copying the name would leave two entities with the same name, and
`find_components(name=…)` would return both. Ids still change, and the docstrings say so.

### 6.4 One operation wrapper (M-16)

`Helpers::Operation.run(model, label) { … }` starts the operation, runs the block, builds the
response **before** `commit_operation`, commits, and aborts in an `ensure` when the block did not
complete — for any exception, not only `StandardError`. `safe_abort` moves into it from
`Handlers::Geometry`. All mutating handlers use it. Module instance variables that serve as
hidden result channels (`@_last_stats`) become return values where the wrapper makes that
natural. `test/test_operation_names.rb` and the scan in `test/test_handler_atomicity.rb` are
updated deliberately.

### 6.5 Search by definition name (M-17)

`find_components(name=…)` matches the instance name or, for component instances, the definition
name — the name the Outliner shows for components from the 3D Warehouse or an import. Group
definitions are auto-named "Group#N" and are not matched. Component rows in `list_components`,
`find_components` and `get_component_info` carry `"definition": "<name>"`.

### 6.6 MCP surface, screenshot, docstrings (M-12, M-18, M-24; Python only)

- Tool errors reach the client with `isError: true` and unchanged text (`[code] message`; the
  eval-gate message stays verbatim).
- No duplicate `structuredContent` (`structured_output=False` or its equivalent).
- `ToolAnnotations` on every tool (read-only, destructive, idempotent, `openWorldHint: false`).
  A tool is read-only when it changes neither the model nor any file. `_RETRY_SAFE_TOOLS` is
  derived from the read-only annotation; the part-1 contract test that these tools are read-only
  in Ruby stays.
- The server's `instructions` become a condensed version of the strategy prompt (mm, world
  coordinates, verify via `bbox_mm`, typed tools first, refusals); `serverInfo.version` reports
  the package version.
- `get_viewport_screenshot.max_size` ≤ 2000.
- Docstrings and the prompt say: coordinates are world everywhere; ids change after boolean,
  edge and joinery operations while names are kept; shared entities are refused; new objects go
  into an open group; `undo` undoes the last step of SketchUp's shared undo stack, which may not
  be ours, and answers before SketchUp processes it; `eval_ruby` works in inches, opens no undo
  operation, and its `def`s and constants become global; `entity_count` counts top-level
  entities only.

### 6.7 Live checks (hot reload of the handler files; MCP reconnect for the Python side)

The §3 scene with nothing open and with `outer` open: every tool reports the same world bbox;
`transform_component` puts a nested group at the world target in both states, including inside a
rotated parent; a component placed twice refuses edits to its children, and `find_components`
flags them `shared`; with one of its placements open for editing, `create_component` refuses and
`get_model_info.editing` marks the path shared; `find_components` finds a component by its definition name; chamfer and
boolean results keep the target's name.

## 7. Block C — socket authentication and transport (M-06 and riders)

### 7.1 The token

- The plugin generates a token on first start with `SecureRandom` (32 bytes) and keeps it in
  SketchUp's preferences (section `MCPforSketchUp`). The user cannot type their own: the
  challenge-response below is only as strong as the token.
- The token is required **always**, on loopback as well as on a LAN address. The user chose one
  uniform rule over a token file for same-machine setups and over a loopback exemption; the
  exemption would also have left the README's SSH tunnel open to every process on the VM.
- Settings shows the token, read-only, with **Copy** and **Regenerate**. Regenerate asks for
  confirmation, then closes every connected client, so sessions opened with the old token end.
- The client reads `SKETCHUP_MCP_TOKEN` (`config.py`, like the other settings; `examples/` and the
  contract test read it too). With no token set, every tool and `get_version` answer with an
  instruction — copy the token from Settings into `SKETCHUP_MCP_TOKEN` in the MCP client's config
  and restart the client — without opening a connection.

### 7.2 Handshake

A wire-contract change; the floors move in the release PR.

1. Client → `hello {client_version, client_nonce}` (32 random bytes, hex).
2. Server: first the version check, as today (`-32001`), so an old client hears that it must
   upgrade rather than that its token is wrong. Then → `result {server_version, server_nonce,
   server_proof}`, where `server_proof = HMAC-SHA256(token, "sketchup-mcp/1/server" ‖
   client_nonce ‖ server_nonce)`.
3. Client: its own version check of `server_version`, as today; then it compares `server_proof`
   in constant time. On a mismatch it closes the socket and reports that the server at
   `host:port` does not know the token — a wrong token, or not the MCP plugin.
4. Client → `auth {client_proof}`, where `client_proof = HMAC-SHA256(token,
   "sketchup-mcp/1/client" ‖ client_nonce ‖ server_nonce)`.
5. Server: compares with `OpenSSL.fixed_length_secure_compare`. A match → `result {client_id}`,
   and the handshake is complete. A mismatch → `-32003 authentication failed`, the socket is
   closed, and the event is logged at WARN. Python raises `AuthenticationError` (a subclass of
   `SketchUpError`) whose message says where to copy the token from.

Any other method before step 5 completes is refused and closes the socket, as before `hello`
today. The 30-second pre-handshake deadline covers the whole exchange. The token never crosses
the wire; a process that took the port cannot learn it and cannot produce `server_proof`.

What the handshake does not do: it does not encrypt and does not authenticate later messages.
Someone who can sit between the two ends can read and change the traffic after the handshake.
README keeps recommending the SSH tunnel on networks the user does not trust.

### 7.3 Exposure, wording, the eval gate

- One loopback check based on `Addrinfo` (resolving names such as `localhost`), shared by the
  server's bind warning and the Settings dialog. The dialog now warns about any non-loopback
  host, explicit LAN addresses included.
- The bind warning, the Settings text and README's Security model say what the token protects
  (who can connect) and what it does not (the traffic is not encrypted).
- No separate gate that closes `eval_ruby` on a non-loopback bind: with the token required
  everywhere, the port is closed to strangers in every layout.

### 7.4 Transport hardening

- **M-15**: before the handshake completes, a frame larger than 4 KiB is refused in the framing
  layer, before its body is buffered or parsed; queued frames are capped per client; accepts per
  tick are capped, and rejected sockets do not each write a log line.
- **M-13**: the write deadline is checked only when a write makes no progress
  (`IO::WaitWritable`), not before trying.
- **M-14**: `encode_response_body` and `Errors.truncate_params` rescue `JSON::JSONError`, which
  covers `JSON::NestingError`.
- **M-21**: `handshake_rejected`, `auth_failed`, `write_timeout`, `pre_handshake_timeout` and
  `pending_write_overflow` log at WARN; the Python server logs one line at start (version, host,
  port) and accepts `--version`.
- **M-31**: closing the eval gate is persisted first and never rolled back; `Logger.log` escapes
  CR, LF and other control characters; no backtrace goes to a client that has not completed the
  handshake; `SketchUpError` normalises a non-dict `error.data`; `json.dumps(...,
  allow_nan=False)` turns a non-finite number into `-32602`.
- **M-29, strict arguments**: one table of each handler's allowed argument names; an unknown
  argument is `-32602 unknown argument '<name>' for <tool>`. A contract test checks the table
  against the parameters of the tools in `tools.py`.
- **Startup**: the eager connect in the server's lifespan gets its own bound of 5 seconds,
  independent of `SKETCHUP_MCP_TIMEOUT`, so the server starts degraded within Claude Code's
  30-second limit; the lazy connect on the first tool call keeps the full timeout.

### 7.5 Docs and repository

- README (Security model, setup) explains where the token comes from and how to set it for a
  single machine, for the SSH tunnel and for a LAN layout. `CLAUDE.md` covers the handshake, the
  token and `-32003`.
- M-23: README and `CLAUDE.md` stop saying that the Ruby side reads no environment
  (`handlers/export.rb` reads `TEMP` and `TMP`); README drops "supported range"; the texts,
  including the eval-gate message, name the menu **Extensions** (the API call
  `UI.menu("Plugins")` stays).
- M-27: `SECURITY.md` asks for reports through GitHub's private vulnerability reporting. Turning
  that on is a repository setting: the user enables it or approves the API call.

### 7.6 Live checks (a plugin build installed; hot reload does not cover `core/` and `ui/`)

With the token in the session's MCP config, the tools work. A wrong token: `-32003` and the
instruction. No token: the instruction, and no connection. A fake server on another port that
accepts `hello` without knowing the token: the client refuses it at step 3. A 0.4.0 client: the
version message, not an authentication error. Regenerate: connected clients are closed, and
reconnecting needs the new token. A LAN address in Settings: the warning shows. The smoke check
passes with the token.

## 8. Release 0.5.0

A release PR after C, following `docs/release.md`: both sides bumped to 0.5.0 and both floors
raised to 0.5.0; `CHANGELOG.md` started at 0.5.0, and §6 of `docs/release.md` attaches the

## 9. Decisions
